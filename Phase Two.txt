# Phase 2 — Backend Core + Offline Sync

Telecalling CRM · Implementation specification

Phase 2 turns the Phase 1 engine into a reliable, server-connected telecalling system. The Kotlin engine may already capture calls locally, but now the backend must authenticate each device, store calls safely, import and assign leads, manage follow-ups, and synchronize changes without losing or duplicating data.

Your master plan allocates approximately 3 weeks to this phase, assuming Phase 1 has passed its acceptance tests.

## Phase 2 completion criteria

PostgreSQL becomes the source of truth

Validated schema, migrations, indexes, and transactional writes.

Offline sync works end to end

The phone pushes mutations and pulls server changes safely after reconnecting.

Lead operations work

CSV import, phone-number deduplication, round-robin assignment, and follow-ups.

Recordings reach private storage

Presigned uploads, metadata registration, access checks, and retry handling.

## 1. Phase 2 architecture

Android engine — Room outbox

Captured calls · pending dispositions · device heartbeat

NestJS API

Authentication · Devices · Leads · Calls · Sync · Follow-ups

PostgreSQL

Records, transactions, change feed

MinIO / S3

Recording objects

Next.js dashboard and mobile screens

Consume the same API contract; full dashboard work remains in Phase 4.

The central design principle is that PostgreSQL owns shared business state, Room owns durable local work, and the sync protocol connects them. The phone must not need a live connection to save a captured call.

## 2. Task-by-task implementation plan

Task 1 — Authentication and device registration

Days 1–3

Implement device-bound login, access-token validation, rotating refresh tokens, device registration, remote revocation, and heartbeat persistence.

Task 2 — Finalize the database and migrations

Days 2–5

Review the Prisma schema, enforce foreign keys and uniqueness, add indexes, and create repeatable migrations.

Task 3 — Lead import and assignment

Days 4–8

Import CSV files, normalize Indian mobile numbers, deduplicate records, retain import errors, and assign leads to active callers.

Task 4 — Offline synchronization engine

Days 6–12

Implement `/sync/push`, `/sync/pull`, mutation acknowledgments, change-feed cursors, conflict handling, and retry safety.

Task 5 — Dispositions and follow-ups

Days 10–14

Save call outcomes, update lead stages, schedule follow-ups, and create an API response that supports the caller queue.

Task 6 — Recording uploads and coverage reporting

Days 12–16

Create presigned upload URLs, verify upload registration, enforce access controls, and calculate eligible recording coverage.

Task 7 — End-to-end integration and stress testing

Days 16–21

Validate retries, duplicate requests, conflicting updates, delayed synchronization, and recovery after API or database interruptions.

These are estimates within the three-week target, not independent deadlines. Tasks can overlap after their interfaces and schema contracts are agreed.

## 3. Database implementation

Your master plan already defines the main data model. Phase 2 should implement and verify it, not invent a second schema.

### Core entities to finish first

| Entity            | Why it matters in Phase 2                                |
| ----------------- | -------------------------------------------------------- |
| `User`            | Caller, manager, and administrator identities            |
| `Device`          | Active phone, engine version, heartbeat, sync timestamps |
| `RefreshToken`    | Device-bound sessions and revocation                     |
| `Lead`            | Normalized phone number, assignment, stage, version      |
| `LeadAssignment`  | Transfer history and accountability                      |
| `PipelineStage`   | Configurable sales pipeline                              |
| `DispositionType` | Call outcome, resulting stage, follow-up requirement     |
| `CallLog`         | Authoritative server-side call history                   |
| `FollowUp`        | Scheduled callbacks and completion state                 |
| `Recording`       | Object storage key and call association                  |
| `SyncChangeFeed`  | Ordered server changes for offline clients               |
| `AuditLog`        | Record important administrative and assignment actions   |

`Consent`, `MessageTemplate`, `MessageLog`, and `ImportJob` should also be represented where needed by the existing schema, although full WhatsApp processing is a later phase.

### Database rules that must be enforced

- Unique normalized lead phone numbers for the chosen deduplication policy.
- Unique call idempotency identity, such as `(callerId, dedupeKey)`.
- Foreign keys for leads, callers, devices, recordings, and follow-ups.
- Indexes on assignee, stage, due follow-up time, call timestamps, and sync sequence.
- Version fields for conflict detection.
- Transactions for operations that must succeed together.
- Migrations committed to version control; production schema changes run through `prisma migrate deploy`.

Prisma and PostgreSQL transactions are suitable for preserving these multi-record invariants.&#x20;

### Important design choice: lead phone numbers

Normalize Indian numbers into E.164 form before storing them. For example, the same valid mobile number submitted as `9876543210` and `+91 9876543210` should resolve to the same normalized number.

Do not silently discard conflicting lead data during import. Store an import result that identifies whether a row was created, matched an existing lead, or rejected for validation.

1. Access tokens expire after the configured short lifetime.
2. Refresh tokens are stored as hashes on the server and rotated on use.
3. A refresh token is bound to its device.

## 5. Offline synchronization — the most important part of Phase 2

This is where many offline-first applications fail. A network timeout does not tell the client whether the server committed a mutation. Therefore, the system must support retries without duplicating calls, assignments, or follow-ups.

NestJS's current idempotency guidance also illustrates why durable, shared idempotency storage and atomic operations matter when requests are retried.&#x20;

### 5.1 Push endpoint

`POST /sync/push`

The phone sends a batch of durable, locally queued mutations.

Example request:

```
{
  "mutations": [
    {
      "mutationId": "client-generated-uuid-001",
      "type": "CALL_CAPTURED",
      "createdAt": "2026-10-23T10:30:00Z",
      "payload": {
        "clientCallId": "call-uuid-001",
        "leadId": "lead-uuid-001",
        "durationSec": 84,
        "dedupeKey": "stable-call-key"
      }
    }
  ]
}
```

This is an illustrative payload. The final fields and timestamps must match the shared Zod contract.

The server should:

1. Authenticate the user and device.
2. Validate the mutation type and payload.
3. Check whether the mutation has already been processed.
4. Apply the business operation inside an appropriate database transaction.
5. Record the mutation's result durably.
6. Append any relevant business changes to the change feed.
7. Return a result for every mutation.

Possible per-mutation outcomes:

| Result      | Client behavior                       |
| ----------- | ------------------------------------- |
| `applied`   | Mark acknowledged                     |
| `duplicate` | Mark acknowledged; do not reapply     |
| `conflict`  | Keep visible for resolution           |
| `rejected`  | Stop blind retries; record the reason |

Critical implementation detail: deduplication and the business write must be coordinated atomically. If the call is inserted but the acknowledgment record is not, a retry can create inconsistent behavior. Use a stable mutation ID, unique constraints, and transactions.

### 5.2 Pull endpoint

`GET /sync/pull?cursor=12345`

The server returns changes after the supplied sequence cursor.

Example response:

```
{
  "changes": [
    {
      "seq": 12346,
      "entityType": "Lead",
      "operation": "UPDATE",
      "entityId": "lead-uuid-001",
      "data": {
        "stageId": "qualified",
        "assigneeId": "caller-uuid-002",
        "version": 5
      }
    }
  ],
  "nextCursor": 12346,
  "hasMore": false
}
```

The cursor is a monotonically increasing server change-feed sequence, not a timestamp.

The phone must apply changes durably before advancing its saved cursor. Process the feed in bounded batches and ensure that a failed batch can safely be replayed.

A PostgreSQL sequence alone does not guarantee commit-order visibility across concurrent transactions. Your implementation must explicitly handle late-committing lower sequence values, for example with a serialized change-feed writer or another proven cursor protocol. Otherwise, a client can advance its cursor past a change it has not yet seen.

### 5.3 Conflict rules

Use the policies from your master plan.

| Data                                 | Conflict rule                                      |
| ------------------------------------ | -------------------------------------------------- |
| Calls                                | Append-only; duplicate ingestion is idempotent     |
| Dispositions                         | Versioned; stale edits need attention              |
| Manager assignment and stage changes | Manager's authoritative changes win                |
| Caller-editable lead fields          | Merge field by field under defined ownership rules |
| Follow-ups                           | Last write wins; completion must never revert      |
| Device registration                  | One active device per caller under the v1 policy   |

For Phase 2, write automated tests for these rules before connecting the full caller UI.

The import result should report:

### Round-robin assignment

Use only active, eligible telecallers. The assignment algorithm should run on the server, not independently on each phone.

For example, if the eligible callers are A, B, and C, the next unassigned leads rotate A → B → C → A. Concurrent import jobs must not assign the same lead twice or corrupt the rotation state.

Persist every transfer in `LeadAssignment`, including the previous owner, new owner, reason, and timestamp.

### Queue endpoint

`GET /me/queue`

The queue should return due follow-ups first, then eligible new leads ordered by configured priority and age. Exclude leads that are on DND, outside the permitted calling window, or assigned elsewhere.

A returned lead is not automatically reserved indefinitely. If your workflow requires exclusive calling, introduce an explicit server-side claim or lease with expiry and conflict handling.

## 7. Dispositions and follow-ups

The server should control disposition behavior using configuration, rather than hardcoding sales rules in the mobile app.

For each disposition, support:

- Display label and active status.
- Optional resulting pipeline stage.
- Whether a follow-up is required.
- Whether a remark is required.
- Optional WhatsApp template association for the later messaging phase.

Example configuration:

| Disposition    | Resulting stage  | Follow-up    |
| -------------- | ---------------- | ------------ |
| Interested     | Qualified        | Required     |
| Call later     | Contacted        | Required     |
| Not interested | Closed / lost    | Optional     |
| No answer      | New / attempting | Configurable |

These are examples; your team should define the final values.

When a disposition is saved, apply the relevant changes transactionally: update the call's disposition, update the lead if appropriate, create or update its follow-up, record the consent/disclosure audit where applicable, and publish changes to the sync feed.

The server must validate the follow-up time and enforce calling-hours and DND rules when a future action is executed. A saved follow-up is not permission to call outside permitted hours.

## 10. Phase 2 security requirements

Before the phone can synchronize production data, verify these controls:

- All API requests use HTTPS.
- Access and refresh tokens are handled securely.
- User roles are checked server-side.
- Device ownership is verified on every device-specific operation.
- CSV imports enforce size, format, and row validation limits.
- Lead access is restricted to the appropriate caller or manager scope.
- Call-log uploads are restricted to eligible CRM-related calls.
- Recording uploads and playback use private storage and short-lived authorization.
- Sync mutations are idempotent and transactionally applied.
- Audit events capture sensitive administrative changes.
- Test and production secrets are separate.
- Backups and database recovery have been tested.

Remember that a device-bound token identifies an authorized session; it does not guarantee that every item in the request is legitimate. Validate ownership and relationships on the server.

## 11. Phase 2 testing plan

Before proceeding to Phase 3, run the following tests against a real PostgreSQL instance and the Phase 1 Android engine.

| Test                  | Procedure                                           | Pass criteria                                                 |
| --------------------- | --------------------------------------------------- | ------------------------------------------------------------- |
| Duplicate call push   | Push the same call 10 times                         | One server call record                                        |
| Lost HTTP response    | Commit a mutation, simulate a lost response, retry  | Existing result returned; no duplicate                        |
| Offline batch         | Queue 50 calls, reconnect and sync                  | All 50 acknowledged                                           |
| Partial batch failure | Fail several mutations in a batch                   | Successful rows remain acknowledged; failed rows retry safely |
| Lead deduplication    | Import the same phone in different formats          | One normalized lead under the chosen dedupe policy            |
| Concurrent assignment | Run multiple assignment requests                    | No double ownership; assignment history is correct            |
| Cursor pagination     | Pull multiple pages while new changes are committed | No changes silently skipped                                   |
| Token rotation        | Refresh and replay an old refresh token             | Rotation and reuse policy enforced                            |
| Recording retry       | Retry upload registration                           | One recording association per intended file                   |
| Conflict handling     | Reassign a lead while the phone is offline          | Server assignment wins on the next pull                       |
| Database recovery     | Restart the API during pending sync                 | Committed records remain intact                               |
| Access control        | Attempt cross-caller lead and recording access      | Unauthorized access is rejected                               |

## 13. What happens after Phase 2?

Phase 3 — Caller UI

Offline lead queue, local read model, mandatory disclosure script, disposition sheet, pending-mutation overlay, follow-up reminders, and 72-hour offline lease.

Phase 4 — Manager dashboard

Lead management, caller performance, live polling, follow-up calendar, device health, and recording playback.

For your project, I recommend not building Phase 3 until the sync protocol is stable. The caller interface will depend heavily on reliable mutation acknowledgments, cursor handling, conflict resolution, and durable local state.

One final distinction: Phase 2 delivers the backend and synchronization foundation, not the entire finished CRM. The dashboard, auto-dial workflow, WhatsApp messaging, and production pilot still follow.

For implementation, the next concrete step is to inspect your current `apps/api/prisma/schema.prisma`, the existing `apps/api/src/sync/` module, and the mobile engine's outbox implementation. That will establish which Phase 2 components need to be written and which only need to be tested or corrected.
