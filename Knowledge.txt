Short version: on current Android, third-party apps mostly don't record call audio themselves. They use one of these workarounds:

1. **Mic or speaker capture through an accessibility service.** Android blocked normal call recording in version 6 and microphone recording during calls in version 10, so apps started using the Accessibility API instead. Google Play banned that in 2022. ACR Phone's own page spells out the result: the version installed outside Play, with its accessibility helper, records from the mic or speaker, while the Play version records silence on Android 10+. Quality is poor, since the other person is only audible if the speaker is on.

2. **Root modules.** The same page says a module on a rooted phone gives real two-way recording. That's no use for a fleet of employee phones.

3. **Syncing the phone's own recordings.** Callyzer says it doesn't record at all. The phone does, and Callyzer syncs the files. TeleCRM does something similar, and its docs show the catch: recordings made by Google's dialer can't be synced, the phone needs a compatible dialer, and Wi-Fi Calling can break the sync. This is the practical option for a business app.

4. **Server-side recording.** With cloud telephony the provider records the call on its own servers, so nothing is needed on the phone.

The root cause is that only dialers that ship with the phone, or come from Google, can access call audio. Third-party apps, including third-party dialers, can't. Google also says its policy targets recording where the other person is unaware, so tell customers calls are recorded.

For a fleet installed by APK, that saves reinstalling on every phone. Any Kotlin change still needs a new APK.

**What it costs**
- The hard part is still Kotlin. Expo saves you the screens, not the engine.
- You'd have two toolchains (Gradle and Metro), a JavaScript-to-native bridge to debug, and a new Expo SDK every few months to keep up with. You also can't use Expo Go, so you'd always run a development build.
- If you later become the default dialer, the in-call screen has to be native Kotlin anyway.

**My pick:** Both work. Choose Expo if the team is TypeScript-first and you want over-the-air fixes. Choose pure Kotlin if you have Android skills or expect to become the default dialer. You don't have to decide yet, because step 2's proof of concept is the Kotlin engine with a bare debug screen either way. Once capture passes the three-phone test, put it behind Expo screens or Compose screens.

You're mostly right, with a few exceptions. OOP should be a tool here, not a rule.

**Dependencies: your instinct is sound.** Every package is something you must update, secure, and replace if it's abandoned. We saw this earlier: the React Native call libraries hadn't been updated since 2019 to 2022, and `tsup` is now unmaintained. For a one-developer project, fewer dependencies means less breakage.

**Rule of thumb**
- **Write it yourself** if it's small (roughly under 50 lines), has no security or correctness traps, and is core to your product.
- **Use a library** if it's security-critical (password hashing, JWT, encryption), a standard with many edge cases (CSV, time zones), or a first-party platform library (Android Jetpack, Expo's own modules).
- **Before adding any package,** check that it's maintained, small, and widely used. Wrap it behind your own small interface so you can swap it later.

**Applied to our stack**

| Item | My opinion |
|---|---|
| Passwords, JWT, encryption | Always use a proven library. Never write your own. |
| NestJS, Prisma, Zod, Next.js, Expo | Keep. They're the foundation, and replacing them costs more than it saves. |
| Room, WorkManager | Keep. They're first-party Android libraries, not heavy packages. |
| Phone-number library | If every lead is an Indian mobile number, a ~30-line function may be enough: strip non-digits, handle +91, 91, and 0 prefixes, and check for 10 digits starting 6 to 9. Switch to libphonenumber when you handle landlines or international numbers. |
| OpenAPI-generated Kotlin client | Skip it. The engine calls about six endpoints (sync pull and push, token refresh, heartbeat, upload URL), so a hand-written OkHttp client is simpler. Add a contract test to catch drift. |
| Redis + BullMQ | Trim first. At 50 callers, a jobs table in Postgres (or a small library such as pg-boss) is enough, and it removes one service to run. |
| Live dashboard via SSE | Start with polling every few seconds, and add SSE later. |
| shadcn/ui, Recharts | Start with plain tables, and add charts when managers ask. |
| Self-hosted OTA update server | Defer it. Ship APK updates first. |
| CSV parsing | Use a small library, because quoting and encodings have many traps. |
| Offline sync | Custom code on purpose (cursor plus mutation log). Avoid big sync frameworks, but test it heavily, since sync bugs are the hardest to find. |

I included Redis and a few others as the conventional choice, not because v1 needs them.

**OOP: use it where it fits, not everywhere**
- **NestJS backend:** Yes. Controllers, services, and providers are classes with dependency injection. That's how the framework works.
- **Kotlin engine:** Yes, lightly. Use small classes behind interfaces (Dialer, CallWatcher, Reconciler, Outbox, SyncWorker) so you can test with fakes.
- **Pure logic:** Use plain functions for number normalization, outcome mapping, dedupe keys, queue ordering, and recording matching. They're the easiest to unit test.
- **Expo screens:** Function components and hooks, not classes.
- **Boundaries that may change:** Put interfaces at `TelephonyProvider`, the messaging provider, and the storage provider.
- **Avoid:** deep inheritance and design patterns for their own sake. Prefer composition and small files.

The goal is simple, boring, testable code.

- **Dependencies:** Install only the Expo modules you use, and avoid heavy JavaScript libraries (charts, UI kits). Keep screens plain.
- **Offline logic:** Keep it in the Kotlin engine, so no JavaScript has to run in the background.
- **Swapping later:** Keep the engine independent, so you can replace the Expo shell later if the test fails.

Yes, it's a good plan. It follows our decisions, and the structure is right: the phase 1 gate, the offline design, the risks, and the dependency rules. I'd keep Expo with the Kotlin engine, Postgres with a jobs table, and the build order. But I found problems to fix before you start, most important first.

**Fix before starting**

1. **The phone assumption is shaky.** The plan says "Samsung or Xiaomi". TeleCRM's own guides say Samsung has one of the most reliable recording-sync setups, but only when Samsung's dialer is the default, since Google's dialer or Truecaller breaks it. They list Oppo, Realme, Vivo, Xiaomi, and OnePlus among phones whose default dialer is Google's, whose recordings third-party apps can't read. TeleCRM then needs a separate dialer app, and if that isn't compatible, recording can't be synced. Sell.do's guide says Samsung, Xiaomi, and Vivo typically expose recordings, but phones using Google's dialer don't. The evidence on Xiaomi is mixed, so pick **one Samsung model** for v1 and treat Xiaomi as unproven until tested. TeleCRM's device guide also wants the manufacturer's dialer and at least 4 GB RAM and 64 GB storage. Add to the setup checklist:
   - The manufacturer dialer is the default.
   - Wi-Fi Calling is off, since it commonly breaks sync.
   - One recorded call is made first, since Samsung only creates the recordings folder after the first recorded call.
   - Android lets your app be granted that exact folder. Test this in Phase 0.

2. **The cloud fallback is promised but never planned.** "In v1" lists cloud telephony as the fallback for phones that can't record, "Not in v1" excludes it, and no phase builds it. For v1, reject phones that fail the recording test and drop the fallback from v1. Add a cloud phase (provider, webhooks, consent, cost, about 2 to 3 weeks) only if the gate fails.

3. **Recording volume isn't costed.** Assume 0.5 MB per recorded minute and 3-minute calls (measure your phones). Then 7,500 calls a day with about 40% connecting is roughly 4.5 GB a day, or about 11 GB a day if all connect, which is over a terabyte a year. Each phone would upload roughly 90 to 225 MB a day. So upload on Wi-Fi by default, measure real file sizes in Phase 0, and add retention period and who may play recordings to your open decisions.

4. **"Every call has a recording" can't be true.** Unanswered calls have none. Define coverage as connected calls above a minimum duration (for example 10 seconds), and flag "missing recording" only for those.

5. **Compulsory recording needs a consent design now,** not just a legal review at the end. The phone's recorder won't announce anything to the customer. Decide the process in Phase 3, such as a script on the lead card and a Consent record of type RECORDING. I'm not a lawyer, so have someone qualified review it.
