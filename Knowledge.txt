Short version: on current Android, third-party apps mostly don't record call audio themselves. They use one of these workarounds:

1. **Mic or speaker capture through an accessibility service.** Android blocked normal call recording in version 6 and microphone recording during calls in version 10, so apps started using the Accessibility API instead. Google Play banned that in 2022. ACR Phone's own page spells out the result: the version installed outside Play, with its accessibility helper, records from the mic or speaker, while the Play version records silence on Android 10+. Quality is poor, since the other person is only audible if the speaker is on.

2. **Root modules.** The same page says a module on a rooted phone gives real two-way recording. That's no use for a fleet of employee phones.

3. **Syncing the phone's own recordings.** Callyzer says it doesn't record at all. The phone does, and Callyzer syncs the files. TeleCRM does something similar, and its docs show the catch: recordings made by Google's dialer can't be synced, the phone needs a compatible dialer, and Wi-Fi Calling can break the sync. This is the practical option for a business app.

4. **Server-side recording.** With cloud telephony the provider records the call on its own servers, so nothing is needed on the phone.

The root cause is that only dialers that ship with the phone, or come from Google, can access call audio. Third-party apps, including third-party dialers, can't. Google also says its policy targets recording where the other person is unaware, so tell customers calls are recorded.

For a fleet installed by APK, that saves reinstalling on every phone. Any Kotlin change still needs a new APK.

**What it costs**
- The hard part is still Kotlin. Expo saves you the screens, not the engine.
- You'd have two toolchains (Gradle and Metro), a JavaScript-to-native bridge to debug, and a new Expo SDK every few months to keep up with. You also can't use Expo Go, so you'd always run a development build.
- If you later become the default dialer, the in-call screen has to be native Kotlin anyway.

**My pick:** Both work. Choose Expo if the team is TypeScript-first and you want over-the-air fixes. Choose pure Kotlin if you have Android skills or expect to become the default dialer. You don't have to decide yet, because step 2's proof of concept is the Kotlin engine with a bare debug screen either way. Once capture passes the three-phone test, put it behind Expo screens or Compose screens.

**Rule of thumb**
- **Write it yourself** if it's small (roughly under 50 lines), has no security or correctness traps, and is core to your product.
- **Use a library** if it's security-critical (password hashing, JWT, encryption), a standard with many edge cases (CSV, time zones), or a first-party platform library (Android Jetpack, Expo's own modules).

6. Recommended TelephonyEngine processing logic
This is the central business logic I would implement in TelephonyEngineModule.kt.

The following is conceptual Kotlin-style pseudocode, not a replacement for your existing implementation.
suspend fun processCall(call: DetectedCall) {

    // 1. Check whether call came from CRM
    val crmLeadId = call.crmLeadId

    // 2. Resolve lead
    val lead = if (crmLeadId != null) {
        leadRepository.findById(crmLeadId)
    } else {
        val number = phoneNormalizer.normalize(
            call.phoneNumber,
            defaultRegion = "IN"
        )

        if (number == null) return

        leadRepository.findByNormalizedPhone(number)
    }

    // 3. Unknown calls are not persisted
    if (lead == null) {
        return
    }

    // 4. Apply configured SIM/account restrictions
    if (!simPolicy.isAllowed(call.phoneAccount)) {
        return
    }

    // 5. Validate call data and duplicate status
    if (!callValidator.isValid(call)) {
        return
    }

    if (callRepository.alreadyProcessed(call.sourceId)) {
        return
    }

    // 6. Persist eligible call and Outbox event atomically
    database.withTransaction {
        callRepository.insert(
            call.toCallRecord(lead.id)
        )

        outboxRepository.enqueue(call.sourceId)
    }
}


There are some important implementation details:
- crmLeadId must be verified against the current local lead cache, not blindly trusted.
- The SIM policy should run before persistence.
- sourceId must be a stable identifier for the detected event.
- A CRM-initiated call should not be duplicated when the native call-log reconciliation later detects the same call.
- If a call's outcome is not yet available, avoid creating misleading analytics.
- Unknown calls should be discarded without logging their number in application logs, crash reports, or analytics.
One correction to the original filtering suggestion
Don't necessarily fetch the entire historical call log just to filter it afterward.

If automatic call detection is permitted and available, use incremental reconciliation:
1. Read only the newest unprocessed call-log entries needed for reconciliation.
2. Process them locally.
3. Match eligible leads.
4. Persist eligible records only.
5. Advance the reconciliation cursor safely.
This is different from bulk-importing the phone's entire call history. Even incremental reading requires appropriate permission and policy eligibility; local filtering does not itself grant permission to access restricted data.

13. Instructions for implementing this in your existing project
I would give your coding agent the following implementation specification:
Implementation Specification: Lead-Gated Call Management
Objective
Refactor the existing Android Telephony Engine to implement privacy-first, lead-centric call logging.

The application must not behave as a general-purpose phone call history collector. It must record only eligible business calls associated with registered CRM leads.
1. Call filtering
Implement a centralized call filtering pipeline.

Every detected call must pass through:
1. CRM-origin identification.
2. Lead ID validation.
3. Phone number normalization.
4. Existing lead matching.
5. Configured SIM/account validation.
6. Call validation.
7. Duplicate detection.
8. Local persistence.
9. Outbox synchronization.
2. Lead matching
- Prioritize a verified CRM lead ID.
- Otherwise normalize the phone number using Google's libphonenumber.
- Use E.164 format.
- Match against primary and alternate lead phone numbers.
- Handle multiple matching leads without arbitrary selection.
- Do not persist calls with no valid lead association.
3. Privacy requirements
- Do not bulk-import historical phone calls.
- Do not persist unmatched calls.
- Do not synchronize unmatched calls.
- Do not upload personal call metadata or recordings.
- Do not include phone numbers in debug logs or crash reports unnecessarily.
- Make unknown-number handling disabled by default.
- Keep call recording separate from call metadata tracking.
4. SIM handling
- Support optional employee-configured Work SIM identification.
- Use Android phone-account information where available.
- Do not assume SIM 1 is the Work SIM.
- Handle SIM changes and unavailable account identifiers.
- Apply SIM filtering only when explicitly configured.
5. Database and synchronization
- Store only validated, matched business calls.
- Associate each call with a valid lead ID and employee ID.
- Create the local call record and Outbox event atomically.
- Prevent duplicate call records during reconciliation.
- Implement reliable retry and synchronization.
- Preserve existing database migrations and historical CRM data.
6. CRM integration
- Display calls inside the individual lead activity timeline.
- Provide a global Lead Calls screen.
- Separate incoming, outgoing, answered and missed calls.
- Create missed-call follow-up tasks for eligible existing leads.
- Prevent duplicate follow-up tasks.
- Provide manual call logging as a fallback.
7. Google Play and privacy
- Verify eligibility for the enterprise CRM Call Log permission exception before retaining restricted permissions.
- Provide the required corporate login and disclosures where applicable.
- Do not assume local filtering alone makes permission usage compliant.
- Provide a functional fallback when permission is unavailable.
8. Non-negotiable development constraints
- Inspect the complete existing TelephonyEngineModule.kt before modifying it.
- Review all related repositories, database entities, workers, services and permission declarations.
- Preserve existing business logic and working functionality.

- Do not introduce duplicate database tables unnecessarily.
- Do not bypass the existing Outbox synchronization architecture.
- Maintain compatibility with existing stored records and migrations.
- Provide complete updated files, not partial code snippets.
