# Phase 1 — Kotlin Telephony Engine Proof

Telecalling CRM · Technical implementation specification · Android-first

Phase 1 is the most important phase of your Telecalling CRM project. Before building the complete caller app, manager dashboard, WhatsApp automation, or auto-dialer, you must prove that your Android engine can reliably handle real SIM calls, capture call logs, match recordings, survive app interruptions, and synchronize data without losing or duplicating calls.

The objective is to prove the riskiest part of the entire system before investing in the rest.

## Phase 1 exit criteria

# 50

Test calls captured

# 0

Lost calls or duplicate records

# ≥95%

Recording match rate on supported devices

# 4+

OEM families tested with real phones

These are the proposed acceptance targets from your master plan. Test all relevant failure scenarios, not just 50 consecutive successful calls.

## 1. What exactly are we building?

We are building a small native Android engine inside your Expo application. For this phase, it will have a basic diagnostic screen rather than a polished telecaller interface.

The screen will let you:

- Detect the phone manufacturer and Android version.
- Inspect available SIM subscriptions.
- Select a SIM and initiate an outgoing call.
- Detect call-state changes and retrieve the resulting system call-log entry.
- Store captured calls in a durable local database.
- Find stock dialer recordings through a user-granted folder permission.
- Match recording files to calls and upload test data to the backend.
- Reconcile calls missed while the app was closed.
- Inspect sync status, permissions, and diagnostics.

The initial deliverable is a working proof-of-concept APK, not the complete production CRM.

### Target architecture

Expo diagnostic screen

SIM list · Dial · Call results · Recordings · Diagnostics

Kotlin Telephony Engine

Dialer · Call watcher · Call-log reader · Reconciler

Room outbox · WorkManager · SAF recording scanner

Android operating system

Native dialer · SIM services · CallLog provider · Recorder files

Test backend and storage

HTTPS API · PostgreSQL · MinIO/S3-compatible storage

The key separation is that the Kotlin engine owns telephony and durable background work; Expo owns the interface. The UI must not be responsible for preserving call records while it is closed.

## 2. Phase 1 scope: what is included and excluded

| Included in this phase                   | Deferred to later phases                    |
| ---------------------------------------- | ------------------------------------------- |
| Native Kotlin Expo module                | Complete caller experience                  |
| Outgoing calls using the chosen SIM      | Auto-dial queue and countdown               |
| Call-state and call-log capture          | Full manager dashboard                      |

The goal is to prove the engine's interfaces and behavior. Avoid spending time on visual design or implementing every backend module before the native calling and recording risks are understood.

## 3. Phase 1 task breakdown

The following order minimizes wasted effort. Do not begin with recording uploads or the UI polish. First prove that Android can reliably capture the call.

Task 1 — Create the native engine skeleton

Days 1–3 · Foundation

Create the local Expo module, Kotlin classes, manifest configuration, and a debug screen. Confirm that JavaScript can invoke Kotlin methods and receive events.

Task 2 — SIM discovery and calling

Days 3–6 · Telephony

Discover SIM subscriptions, initiate calls through the system telephony framework, and verify SIM selection on dual-SIM phones.

Task 3 — Call watcher and reconciliation

Days 5–10 · Reliability

Observe call-state transitions, read the system call log, correlate entries, persist them, and recover missed events after process death.

Task 4 — Room outbox and background work

Days 8–12 · Durability

Store captured calls transactionally, enqueue upload work, retry failures, and survive reboot or connectivity loss.

Task 5 — OEM recording discovery and matching

Days 10–17 · Highest-risk feature

Obtain SAF folder access, scan actual files, match them to calls without guessing, and validate upload eligibility.

Task 6 — Sync, heartbeat, and diagnostics

Days 15–20 · Integration

Connect to the test API, upload test recordings, track synchronization status, and collect device diagnostics.

Task 7 — Failure testing and release candidate

Days 18–25 · Acceptance

These are working estimates, not guaranteed durations. Your master plan budgets 3–4 weeks for Phase 1. The task estimates above overlap where sensible; a difficult OEM recorder or background-execution problem can extend the schedule.

## 5. Task 2 — SIM discovery and outgoing calls

This task must use the manufacturer's native dialer. The app is not implementing its own in-call screen.

### 5.1 Discover SIMs

Use Android's `SubscriptionManager` to obtain active SIM subscription information. Each subscription can expose a subscription ID, slot index, carrier name, and display label, subject to OS version and permission restrictions.

Internally, keep a distinction between:

- `subscriptionId`: Android's active subscription identifier.
- `slotIndex`: physical/logical SIM slot index.
- `phoneAccountHandle`: Telecom's account identifier used for routing.

Do not assume SIM 1 always has subscription ID `1`, or that SIM labels uniquely identify an account. These identifiers can change after SIM replacement or configuration changes.

### 5.2 Place a call

Use Android Telecom's `TelecomManager.placeCall()` with the selected `PhoneAccountHandle` supplied through the appropriate call extras, or an equivalent supported system-dialer integration. The system's routing behavior must be verified on real dual-SIM devices.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://developer.android.com\&sz=32)

Android Developers

+1



The engine should:

1. Validate the lead ID and destination number.
2. Normalize the number for India.
3. Confirm the selected SIM still exists.
4. Persist a pending dial attempt with a generated ID.
5. Initiate the call.
6. Record the attempt timestamp and chosen subscription.
7. Wait for call-state and call-log reconciliation to establish the actual call record.

Important: Starting a call is not proof that it connected. Likewise, selecting a SIM in your app is not proof that the carrier actually routed the call through that SIM. Validate the actual system call-log entry and the device's behavior.

### 5.3 Call-state detection

Use `TelephonyCallback` on Android 12+ and the compatible `PhoneStateListener` path on older supported Android versions.

The state listener helps determine when a call is dialing, ringing, active, or disconnected, subject to what the platform exposes. It does not replace the call log.

The system call log is the authoritative source for the final duration and call type where available.

| Event                   | Engine action                                |
| ----------------------- | -------------------------------------------- |
| Dial requested          | Persist dial attempt                         |
| Call begins             | Record observed state                        |
| Call disconnects        | Schedule call-log lookup                     |
| Entry not yet available | Retry with bounded backoff                   |
| Entry found             | Normalize and deduplicate                    |
| Entry never found       | Retain unresolved attempt for reconciliation |

A call with duration greater than zero is classified as connected under the v1 rules. A zero-duration outgoing call is not connected; Route A cannot reliably distinguish busy, rejected, and unanswered calls.

### 5.4 Permissions and distribution

The engine needs a carefully reviewed permission plan for `CALL_PHONE`, call-state observation, call-log access, and notifications where applicable. Request runtime permissions at the moment their purpose is explained.

One major design constraint deserves special attention: Google Play restricts call-log permissions to qualifying default Phone or Assistant handlers. Your plan assumes direct APK distribution, but that does not automatically grant unrestricted access to call logs. The actual permission grant and Android behavior must be validated on the target OS and devices.&#x20;

## 6. Task 3 — Call-log capture and reconciliation

This is the reliability core of the engine.

Android can deliver call-state notifications while the app is running, but notifications alone are not a durable record of every call. The app might be killed, a callback might arrive late, or a call-log row might not be immediately visible.

The solution is to use two independent mechanisms:

- Live capture: react to the call ending and look for the corresponding call-log entry.
- Reconciliation: periodically scan the system call log and discover entries not yet stored in Room.

### 6.2 Match calls carefully

Use a combination of:

- Normalized phone number.
- Approximate start time.
- Direction.
- SIM/subscription information where available.
- System call-log entry ID.
- An application-generated dial-attempt ID when available.

Do not match only by phone number: a caller may call the same lead several times in one shift.

For an engine-initiated call, correlate against the saved dial attempt. For an entry discovered during reconciliation, use the call-log metadata and stable identifiers available on that device.

Your master plan proposes this dedupe key:

```
hash(deviceId + callLogEntryId + startedAt + numberE164)
```

Keep the server's unique constraint on `(callerId, dedupeKey)`. However, distinguish the dedupe key from the call's business ID. The local record should have a stable client-generated UUID that survives retries and is used by the server for idempotency.

### 6.3 What reconciliation must do

Run reconciliation:

1. At app startup.
2. After a call finishes.
3. When the telecaller resumes their shift.
4. Periodically using WorkManager.
5. After the phone returns online, if there are unresolved local records.

Use a persisted watermark, overlapping lookback window, and deduplication. Do not assume a timestamp-only watermark is sufficient: multiple calls can have identical or close timestamps, and system entries may appear late.

A safe conceptual algorithm is:

```
read saved watermark
query call log with an overlap window
for each eligible entry:
    normalize number
    derive stable local identity
    insert call if absent
    enqueue upload if not acknowledged
advance watermark only after durable processing
```

The watermark must not advance past entries that were not durably handled. For this phase, make the scan incremental, but retain enough overlap to catch delayed entries.

### 6.4 Store only relevant calls

Your master plan requires the engine to upload calls associated with CRM leads or calls it initiated itself. Personal calls to unrelated numbers should not be uploaded.

This means you need a clear matching policy before sending any call log data to the server. Keep raw diagnostic data local and short-lived; do not send an employee's entire personal call history to the backend.

Task 3 passes when: the same calls are captured correctly whether the app is open, backgrounded, or killed and reopened, with zero duplicates across repeated reconciliation.

## 7. Task 4 — Room database and durable outbox

The Kotlin engine must remain reliable even when the Expo screen is closed. Store call data in Room, which provides structured SQLite persistence and DAO-based access.&#x20;

### 7.1 Minimum local tables

For Phase 1, use three principal entities rather than implementing the entire production schema immediately.

| Table                | Purpose                                        |
| -------------------- | ---------------------------------------------- |
| `CapturedCall`       | Finalized call metadata and disposition status |
| `OutboxMutation`     | Durable pending server mutations               |
| `RecordingCandidate` | Discovered files awaiting matching or upload   |

Example call record:

```
CapturedCall
  id: UUID
  deviceId: String
  callLogEntryId: Long?
  leadId: String?
  numberE164: String
  direction: OUTGOING | INCOMING
  startedAt: Long
  endedAt: Long
  durationSec: Int
  outcome: CONNECTED | NOT_CONNECTED | MISSED | REJECTED
  simSubscriptionId: Int?
  recordingStatus: PENDING | MATCHED | MISSING |
                   NOT_APPLICABLE | UNSUPPORTED_DEVICE
  syncStatus: PENDING | ACKNOWLEDGED
  createdAt: Long
```

Treat the example as a design sketch, not a final Room entity. Android's call-log types and fields vary by platform version, so outcome mapping must explicitly handle unknown values.

### 7.2 Transactional writes

When a call is captured:

1. Begin a Room transaction.
2. Insert the call record if it does not exist.
3. Insert the corresponding outbox mutation.
4. Commit both changes.
5. Emit the UI event after the commit succeeds.

This prevents a crash between storing a call and queuing it for synchronization from silently losing the upload job.

### 7.3 Outbox states

PENDING

Queued locally

IN_FLIGHT

Being uploaded

ACKNOWLEDGED

Server confirmed

Failures return to a retryable state. Conflicts or permanent rejections remain visible for investigation; they must never be silently discarded.

The actual implementation should use explicit state transitions and lease/recovery rules so a process death cannot leave mutations stuck forever in `IN_FLIGHT`.

### 7.4 WorkManager

Use WorkManager for persistent work such as reconciliation, heartbeat, synchronization, and recording scans. It supports retry and backoff policies.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://developer.android.com\&sz=32)

Android Developers



Recommended constraints:

- Network connectivity for server synchronization.
- Wi-Fi for recording uploads by default.
- Exponential retry backoff.
- Unique work names to prevent redundant workers.
- Small, bounded batches for API mutations.
- A recovery path for interrupted uploads.

Do not rely on WorkManager as an exact timer. It schedules persistent work, but Android may defer execution because of battery and background restrictions.

Task 4 passes when: a forced process death or network outage leaves all committed calls intact, and reconnecting causes them to synchronize without duplicates.

## 8. Task 5 — Universal OEM recording discovery

### 8.3 Recording matching algorithm

The matching logic should be conservative.

```
for each new audio file:
    inspect metadata available through SAF
    parse filename using configured OEM patterns
    normalize any phone number found
    find candidate calls within the time tolerance
    compare phone number and other available evidence
    if exactly one credible candidate:
        attach file to call
    else:
        leave file pending for manual review
```

Use filename patterns as evidence, not as the sole source of truth. The master plan's patterns for Samsung, Xiaomi, Vivo, and Oppo-family devices should be configuration entries, with a tested fallback for unknown formats.

A file must never be attached to a call simply because it is the nearest recording by time.

### 8.4 Recording status rules

| Situation                                                            | Status               |
| -------------------------------------------------------------------- | -------------------- |
| Call shorter than 10 seconds or zero duration                        | `NOT_APPLICABLE`     |
| Supported recording device, eligible call, matched file              | `MATCHED`            |
| Supported device, eligible call, no file after the evaluation window | `MISSING`            |
| Google Dialer with no accessible recording                           | `UNSUPPORTED_DEVICE` |
| File or call has not yet been fully evaluated                        | `PENDING`            |

Do not mark a recording `MISSING` immediately after hang-up. Use a bounded grace period and repeated scans to allow the dialer to finish writing its file.

The coverage metric should be:

\\[ \text{Coverage} = \frac{\text{Eligible connected calls with matched files}} {\text{Eligible connected calls on supported devices}} \times 100\\% \\]

Calls below 10 seconds are excluded, as are devices explicitly classified as unsupported. Report the unsupported-device percentage separately so the 95% target cannot be met merely by excluding too many phones.

### 8.5 Recording upload

For Phase 1, upload a small set of test recordings:

1. Obtain an authorized upload URL from the API.
2. Stream the SAF content to object storage using a bounded-memory upload strategy.
3. Verify the uploaded object and its size.
4. Register the recording against the correct call.
5. Mark the local upload complete only after server acknowledgment.

Do not load large audio files entirely into memory. Use streaming and retryable upload state. Keep the object storage private, and ensure playback permissions are enforced by the backend.

### 9.1 Design for reliable user recovery

Do not make correctness depend on automatically opening the app.

Instead, implement two layers:

- Durable layer: The engine captures the call and stores it in Room independently of whether the UI is visible.
- Interaction layer: When Android allows it, the app presents the disposition interface. Otherwise, a notification with a user-tappable action brings the user back to the pending disposition.

Test the following states separately:

| Phone state             | Expected behavior                                                      |
| ----------------------- | ---------------------------------------------------------------------- |
| App visible during call | Disposition appears after capture                                      |
| App in background       | Capture persists; UI returns when permitted                            |
| Screen locked           | Capture persists; notification or permitted UI flow prompts the caller |
| Process killed          | Reconciliation recovers the call on next execution                     |
| Phone offline           | Call and pending disposition remain locally stored                     |

Important correction to the original plan: Guaranteed automatic foreground activity launch after every call is not a safe assumption across Android versions and OEMs. Treat it as a tested capability, not an architectural guarantee.

### 9.2 Heartbeat payload

Send a heartbeat to the API at an appropriate interval during active shifts, and on significant state changes.

Example payload:


This is illustrative JSON, not a real device payload. Populate timestamps and diagnostics with actual values. Do not hardcode the example values.

The backend should track `lastSeenAt`, `lastSyncAt`, and clock offset separately. A successful heartbeat does not prove that call synchronization succeeded.
